In the earlier explanation, Spring Boot was mostly **downstream of SAP**: it consumed SAP OData/BAPI/IDoc services. The opposite—and equally important—pattern is **SAP depends on Spring Boot**: SAP calls a Spring Boot API, consumes its events, or delegates airline-specific logic to it. This is a common SAP **side-by-side extension** pattern: the extension runs outside the SAP core, is loosely coupled through stable APIs/events, and is often built on SAP BTP. [learning.sap](https://learning.sap.com/courses/expanding-sap-s-4hana-using-key-user-side-by-side-extensibility/side-by-side-extensibility-in-a-nutshell)

## Direction terminology

| Direction | Meaning | Airline example |
|---|---|---|
| **Spring Boot → SAP** | Spring Boot is upstream; SAP is downstream | Spring Boot sends a baggage fee to SAP for invoicing |
| **SAP → Spring Boot** | SAP is upstream; Spring Boot is downstream | SAP asks Spring Boot: “Is gate C3 available for AI202?” |
| **Bidirectional** | Both systems call each other at different stages | SAP creates a booking event; Spring Boot validates it and SAP later consumes the result |

In your target architecture, **SAP remains the system of record for ERP business objects**, while Spring Boot provides specialized airline logic, external-system connectivity, pricing, availability, fraud checks, or custom workflows that do not belong inside the SAP core.

## When SAP should depend on Spring Boot

Use SAP → Spring Boot when the logic is:

- Highly airline-specific and changes frequently.
- External to SAP’s standard business domain.
- Better implemented in Java/Spring Boot due to existing team skills, libraries, or performance needs.
- Required by multiple SAP and non-SAP systems.
- Unsuitable for direct customization inside SAP’s clean core.

Airline examples:

| SAP needs | Spring Boot responsibility |
|---|---|
| Validate an airport slot request | Check slot availability in an airport slot-management system |
| Calculate a dynamic baggage fee | Apply airline-specific rules, seasonal pricing, loyalty tier, and airport charges |
| Approve a cargo invoice | Check shipment status, customs clearance, and duplicate invoices in the cargo platform |
| Determine a passenger’s rebooking options | Query inventory, fare rules, and partner-airline availability |
| Send a delay notification | Orchestrate SMS, email, push notification, and passenger-preference services |
| Check spare-part availability | Query a maintenance/inventory service and return a decision to SAP |
| Approve a vendor invoice | Apply airline-specific duplicate-check and approval rules before SAP posts it |

SAP’s side-by-side extensibility model explicitly recommends loosely coupled extensions based on remote APIs and events, rather than modifying the S/4HANA core. [learning.sap](https://learning.sap.com/courses/expanding-sap-s-4hana-using-key-user-side-by-side-extensibility/side-by-side-extensibility-in-a-nutshell)

## Spring Boot API design

Keep the Spring Boot API **SAP-friendly**: stable contract, idempotent, versioned, and business-oriented.

```java
@RestController
@RequestMapping("/api/v1/baggage-fees")
public class BaggageFeeController {

    private final BaggageFeeService service;

    public BaggageFeeController(BaggageFeeService service) {
        this.service = service;
    }

    @PostMapping("/calculate")
    public ResponseEntity<BaggageFeeDecision> calculate(
            @Valid @RequestBody BaggageFeeCalculationRequest request) {

        BaggageFeeDecision decision =
            service.calculateBaggageFee(request);

        return ResponseEntity.ok(decision);
    }
}
```

```java
public record BaggageFeeCalculationRequest(
```

## Service layer

```java
@Service
public class BaggageFeeService {

    private final AirportPolicyClient airportPolicyClient;
    private final LoyaltyClient loyaltyClient;
    private final BaggageFeeRepository repository;

    public BaggageFeeService(
            AirportPolicyClient airportPolicyClient,
            LoyaltyClient loyaltyClient,
            BaggageFeeRepository repository) {
        this.airportPolicyClient = airportPolicyClient;
        this.loyaltyClient = loyaltyClient;
        this.repository = repository;
    }

    @Transactional
    public BaggageFeeDecision calculateBaggageFee(
            BaggageFeeCalculationRequest request) {

        AirportBaggagePolicy policy =
            airportPolicyClient.getPolicy(
                request.originAirport(),
                request.flightNo(),
                request.flightDate()
            );

        BigDecimal freeAllowance = policy.baseAllowanceKg();

        if ("GOLD".equals(request.loyaltyTier())) {
            freeAllowance = freeAllowance.add(new BigDecimal("2"));
        }

        BigDecimal chargeableKg = request.checkedInWeightKg()
            .subtract(freeAllowance)
            .max(BigDecimal.ZERO);

        BigDecimal fee = chargeableKg
            .multiply(policy.feePerKg())
            .setScale(2, RoundingMode.HALF_UP);

        BaggageFeeDecision decision = new BaggageFeeDecision(
            chargeableKg.compareTo(BigDecimal.ZERO) > 0
                ? "CHARGE" : "NO_CHARGE",
            freeAllowance,
            chargeableKg,
            fee,
            "INR",
            chargeableKg.compareTo(BigDecimal.ZERO) > 0
                ? "EXCESS_BAGGAGE" : "WITHIN_ALLOWANCE",
            UUID.randomUUID().toString()
        );

        repository.saveDecision(request, decision);

        return decision;
    }
}
```

Here, SAP depends on Spring Boot for the **decision**, while SAP still owns the actual invoice posting and financial document.

## How SAP calls Spring Boot

### Option 1: SAP CPI / SAP Integration Suite

This is usually the cleanest enterprise pattern.

```text
SAP S/4HANA
   → CPI iFlow
   → Spring Boot /api/v1/baggage-fees/calculate
   ← JSON decision
   → SAP posts billing document
```

CPI handles:

- Authentication and certificate exchange.
- SAP payload to Spring Boot JSON mapping.
- Retry and error handling.
- Rate limiting and monitoring.
- Decoupling SAP from Spring Boot API changes.

SAP Integration Suite is designed to connect SAP cloud applications, third-party applications, and on-premise systems, making it a natural control point for this pattern. 

### Option 2: ABAP HTTP call

For a direct synchronous call from ABAP:

```abap
DATA(lo_http_client) = cl_web_http_client_manager=>create_by_http_destination(
    i_destination = cl_http_destination_provider=>create_by_url(
        i_url = 'https://airline-extension.example.com/api/v1/baggage-fees/calculate' ) ).

DATA(lo_request) = lo_http_client->get_http_request( ).

lo_request->set_header_fields( VALUE #(
    ( name = 'Content-Type'  value = 'application/json' )
    ( name = 'Authorization' value = |Bearer { lv_token }| )
) ).

lo_request->set_text( lv_json_body ).

DATA(lo_response) = lo_http_client->execute( if_web_http_client=>post ).

DATA(lv_response) = lo_response->get_text( ).
```

In production, avoid hard-coded URLs and tokens. Use SAP BTP destinations, destination service, or secure configuration.

### Option 3: SAP Event Mesh

For asynchronous processing:

```text
SAP S/4HANA
   → publishes event: BaggageCheckedIn
   → SAP Event Mesh
   → Spring Boot subscriber
   → calculates fee
   → publishes BaggageFeeCalculated
   → SAP consumes result
```

This is better when SAP does not need an immediate synchronous answer. For example, SAP can check in baggage immediately, while Spring Boot calculates and publishes the fee decision asynchronously.

## SAP-side contract expectations

When SAP is the upstream consumer, design Spring Boot for SAP integration requirements:

| SAP expectation | Spring Boot implementation |
|---|---|
| Stable API contract | Versioned REST API: `/api/v1/...` |
| Traceability | Accept and return `correlationId` |
| Retry safety | Idempotency key based on booking + flight + baggage event |
| Clear success/failure | Proper HTTP status and structured error body |
| Low latency | Cache airport policies and reference data |
| Security | OAuth 2.0 client-credentials, mTLS, IP allowlisting where applicable |
| Auditability | Persist request, response, decision, and SAP reference |
| Monitoring | Metrics for latency, error rate, SAP call volume |

### Idempotency example

SAP may retry after a timeout. Spring Boot must not return a different fee or create duplicate downstream effects.

```java
@Idempotent(
    key = "#request.bookingId() + ':' + #request.flightNo() + ':' + #request.passengerId()",
    ttlMinutes = 60
)
public BaggageFeeDecision calculateBaggageFee(
        BaggageFeeCalculationRequest request) {
    ...
}
```

If you do not use a custom annotation, implement it explicitly:

```java
Optional<BaggageFeeDecision> existing =
    repository.findByCorrelationId(correlationId);

if (existing.isPresent()) {
    return existing.get();
}
```

## Error contract for SAP

SAP should receive a predictable error response.

```json
{
  "errorCode": "AIRPORT_POLICY_UNAVAILABLE",
  "message": "Unable to retrieve baggage policy for airport MAA",
  "correlationId": "c8f2-4b21-9d77",
  "retryable": true,
  "timestamp": "2026-10-19T02:20:00Z"
}
```

Spring Boot exception handler:

```java
@RestControllerAdvice
public class SapIntegrationExceptionHandler {

    @ExceptionHandler(AirportPolicyUnavailableException.class)
    public ResponseEntity<SapErrorResponse> handlePolicyUnavailable(
            AirportPolicyUnavailableException ex) {

        return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE).body(
            new SapErrorResponse(
                "AIRPORT_POLICY_UNAVAILABLE",
                ex.getMessage(),
                ex.getCorrelationId(),
                true,
                Instant.now()
            )
        );
    }
}
```

Use:

- `400` for invalid SAP request.
- `401` for authentication failure.
- `403` for authorization failure.
- `404` for unknown booking, flight, or passenger.
- `409` for business conflict.
- `422` for valid syntax but failed business validation.
- `503` for temporary downstream unavailability.
- `500` for unexpected Spring Boot failure.

## Reverse direction: Spring Boot consumes SAP too

In many real airline extensions, the flow is bidirectional:

```text
SAP S/4HANA
   → calls Spring Boot for baggage-fee decision
   → Spring Boot may call SAP OData to verify booking/payment status
   → Spring Boot returns decision
   → SAP creates billing document
```

Example: Before returning a fee, Spring Boot verifies with SAP that the booking is not already invoiced.

```java
public boolean isBookingInvoicedInSap(String bookingId) {
    return sapBookingClient
        .getBooking(bookingId)
        .invoiceStatus()
        .equals("INVOICED");
}
```

So Spring Boot is downstream to SAP for SAP master/transactional data, but upstream to SAP for the baggage-fee decision. Direction depends on the **specific business operation**, not on the product.

## Clean-core boundary

Keep this responsibility split:

| Concern | Owner |
|---|---|
| Financial document creation | SAP |
| Material/inventory posting | SAP |
| Vendor invoice posting | SAP |
| Authorization to post financial data | SAP |
| Airline baggage-pricing policy | Spring Boot |
| Airport slot availability | Spring Boot or airport system |
| Cargo shipment validation | Spring Boot or cargo platform |
| Passenger notification orchestration | Spring Boot |
| Custom airline workflow logic | Spring Boot |
| Integration mapping and security | SAP Integration Suite / API Management |

Do **not** make SAP depend on Spring Boot for core ERP integrity unless there is a clear business reason. If Spring Boot is unavailable, SAP should fail safely, use a cached/default policy, queue the request, or block only the affected non-core operation.

## Resilience patterns

| Pattern | Implementation | Airline example |
|---|---|---|
| Timeout | SAP/CPI sets a 5–10 second timeout | Baggage-fee decision must return quickly at check-in |
| Retry | Retry only idempotent operations | Repeated baggage-fee calculation is safe |
| Circuit breaker | Stop calling Spring Boot during outage | SAP uses last-known policy or standard fee |
| Fallback | Return conservative default | Apply standard 23 kg allowance if dynamic policy is unavailable |
| Outbox | Persist request before processing | Avoid losing baggage-fee requests |
| Dead-letter queue | Store repeatedly failed requests | Failed cargo-invoice validations for manual review |
| Caching | Cache airport policy for 5–15 minutes | Reduce repeated calls during check-in rush |

## Testing from SAP perspective

Test these cases:

| Test | Expected result |
|---|---|
| SAP sends valid baggage request | Spring Boot returns fee decision |
| SAP retries same correlation ID | Same decision returned |
| SAP sends unknown booking | HTTP `404` with structured error |
| SAP sends invalid airport code | HTTP `400` or `422` |
